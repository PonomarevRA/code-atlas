# Эффективное логирование в Python и .NET

Версия инструкции: 1.1. Дата проверки документации: 21 октября 2026.

Инструкция задаёт общий подход для новых сервисов и новых модулей существующих
проектов. Готовые библиотеки отвечают за структурированные сообщения и контекст;
ограниченные очереди и writer отвечают за ввод-вывод. Значения ниже — выбранные
начальные настройки, которые проверяются замерами на целевой машине. Они не
являются результатом сравнительного benchmark библиотек.

## Решения по умолчанию

| Задача | Python | .NET |
| --- | --- | --- |
| Технические логи приложения | `structlog`; стандартный `logging` для сторонних библиотек | `ILogger<T>` и source-generated `LoggerMessage`; Serilog как provider/backend |
| Контекст запроса | `structlog.contextvars` либо явный bound logger | Явные поля, `BeginScope` и настроенная передача scope в Serilog |
| Подготовка JSON | В writer; стандартный serializer сначала, `orjson` только при подтверждённой пользе и совместимой упаковке | В sink/writer; компактный formatter для технических логов, отдельный DTO serializer для журнала |
| История операций с курсором | Отдельный ActivityJournal port и ограниченный sink/adapter | Тот же контракт ActivityJournal и отдельный sink/adapter |
| Дисковая запись | Один writer на журнал; пакеты и ротация сегментов | То же; async sink для обычных логов не заменяет writer журнала |

`Loguru` допустим для небольшого проекта с простыми файловыми логами, но не
добавляется вторым логгером рядом со structlog. Его queue/rotation не заменяют
контракт истории и общей дисковой квоты. Существующий подход проекта не мигрирует
целиком ради внедрения одного нового журнала.

Версии пакетов закрепляются в lock-файле конкретного проекта. Номер версии этой
инструкции не означает совместимость с любой будущей версией библиотеки.

## Технический лог и журнал операций

| Свойство | Технический лог | Activity journal | Обязательный бизнес-аудит |
| --- | --- | --- | --- |
| Назначение | Диагностика сервиса | История действий и состояние интерфейса | Доказуемая фиксация бизнес-события |
| Фильтр уровней | Да | Отдельное включение и coverage, независимо от уровня диагностики | По контракту бизнес-системы |
| Потери при перегрузке | Допускаются со счётчиком | Допускаются со счётчиком и признаком неполноты истории | Не допускаются молча |
| Подтверждение сохранения | Обычно не требуется | Только после определённого контрактом commit | Требуется оговорённая гарантия, например transactional outbox |

Нельзя делать историю операций побочным эффектом `DEBUG`/`INFO`, который исчезает
при смене общего log level на Warning. Observer передаёт типизированный envelope
в ActivityJournal независимо от диагностического logger. Общими могут быть
обогащение контекста, нормализация и адаптер вывода. Результат операции вычисляется
один раз; отдельно запустить поиск или расчёт ради логирования запрещено.

История с допустимыми потерями не переименовывается в надёжный бизнес-аудит.
Для обязательного аудита требуется другой контракт доставки и отказов.

## Правила для прикладного кода

1. Использовать стабильное имя события и именованные поля. Шаблон не формировать
   конкатенацией, интерполяцией запроса пользователя или локализованной строкой.
2. Передавать уже вычисленные простые значения. Не выполнять SQL, HTTP, повторный
   расчёт, обход графа или сериализацию большого объекта исключительно ради лога.
3. Дорогие данные готовить только после проверки уровня/включения нужного
   канала. Аргументы вызова вычисляются до входа в logger, включая generated methods.
4. Не передавать entity/ORM object, request/response, session, исключение или
   произвольный объект в очередь истории. Снимать ограниченную копию разрешённых
   полей: строки, числа, bool, null, короткие разрешённые коллекции.
5. Перед enqueue ограничивать длины и разрешённые поля; после сериализации
   повторно проверять размер события. Учитывать Unicode и JSON escaping.
6. Писать время UTC, длительность измерять монотонными часами, явно указывать
   единицы полей: `duration_ms`, `bytes`, `result_count`. Не вычислять длительность
   вычитанием UTC timestamps.
7. Назначать одного владельца сообщения об ошибке. Повторный throw не порождает
   ещё один одинаковый stack trace на каждом уровне. Для retry допустима
   ограниченная сводка; отмена пользователя не выдаётся за аварийный сбой.
8. Не записывать heartbeat, кадры анимации, каждую строку результата и каждое
   перемещение курсора на диск. Для одной операции достаточно started/finished
   и явно нужных шагов. Массовые детали — только ограниченным opt-in режимом.
9. Не включать по умолчанию stack/callsite inspection, дампы локальных переменных,
   глубокое destructuring и повторное обогащение неизменного контекста.
10. Не дублировать одно и то же полное событие одновременно в console, файл,
    журнал и дополнительный debug-файл без отдельного назначения каждого sink.

Event ID и имя сохраняют смысл после релизов. Переименование полей, изменение
единиц и трактовки outcome — изменение схемы. Числовые ID резервируются в рамках
проекта; ID в примерах ниже иллюстративный. Trace/session/operation ID передаются
как поля, а не как отдельные имена logger или labels метрик.

Тексты запросов хранятся только по принятой политике проекта: ограниченный preview,
fingerprint либо omitted. Маскирование работает на allowlist полей; оно не даёт
универсальной гарантии обнаружения секретов в любом свободном тексте. В MCP
stdout остаётся исключительно каналом протокола.

## Python

### Подготовка события

Для своего кода использовать structlog с заранее настроенной цепочкой
процессоров. Обогащение постоянным контекстом выполняется при создании bound
logger, а не заново вручную в каждом месте. На частых вызовах применяются
`make_filtering_bound_logger` и `cache_logger_on_first_use=True`, если уровни
фиксируются при запуске. Кешированные logger не должны рассчитывать на позднюю
перенастройку. [Рекомендации structlog](https://www.structlog.org/en/stable/performance.html).

Пример фасада технического события; logger уже настроен composition root,
а count/duration получены выполненной операцией:

```python
def log_search_finished(log, operation_id: str, result_count: int,
                        duration_ms: float) -> None:
    """Передаёт вычисленный результат поиска без повторного поиска и файлового I/O."""
    log.info(
        "search.finished",
        event_id=61001,
        operation_id=operation_id,
        result_count=result_count,
        duration_ms=duration_ms,
    )
```

Это пример вызова logger, а не реализация очереди или гарантии persisted.
Для обязательной истории observer вызывает ActivityJournal port отдельно;
техническая запись этого события может быть выключена.

Контекст request/session копируется в envelope до перехода в writer thread.
Writer не читает contextvars вызывающего потока. На границе запроса контекст
очищается или восстанавливается через token/finally, чтобы не смешивать запросы.
В гибридном sync/async приложении перенос контекста проверяется отдельно.
[Context variables](https://www.structlog.org/en/stable/contextvars.html).

### Очередь и обработка

В structlog processor chain до очереди оставить только дешёвую фильтрацию,
захват контекста и bounded-нормализацию. JSON rendering, строковое форматирование
и файловый I/O находятся после очереди. Producer не вызывает `JSONRenderer`,
если этот JSON всё равно будет заново создан writer.

Для стороннего `logging` использовать один согласованный bridge. В стандартном
logging передавать шаблон и аргументы отдельно, например
`logger.info("Found %s nodes", count)`. Дорогие аргументы защищать
`logger.isEnabledFor(logging.DEBUG)`. [Python Logging HOWTO](https://docs.python.org/3/howto/logging.html#optimization).

`QueueHandler`/`QueueListener` можно использовать для диагностики. У стандартного
`QueueHandler.prepare()` форматирование происходит до enqueue; `QueueListener`
переносит обработчики в поток, но сам не объединяет события в write batch.
Для нашего журнала используется собственный адаптер ограниченных envelope,
а не обещание «QueueHandler всё сделает бесплатно».
[Python handlers](https://docs.python.org/3/library/logging.handlers.html#queuehandler).

Логирование не выполняет синхронную запись внутри async handler. Один writer
обслуживает журнал через поток или отдельный согласованный процесс. Обёртка
каждого сообщения в `asyncio.to_thread()`/отдельную task не применяется:
нужна одна ограниченная очередь и управляемый lifecycle writer.

Стандартные FileHandler не обеспечивают координацию независимых процессов.
Для нескольких процессов нужен общий writer через IPC либо согласованный
межпроцессный lock append/rotation. Если процессы запускаются независимо,
обычная очередь одного процесса не становится общей автоматически.
[Python Logging Cookbook](https://docs.python.org/3/howto/logging-cookbook.html#logging-to-a-single-file-from-multiple-processes).

`orjson` — допустимая оптимизация только writer после профилирования. Нужно
проверить правила сериализации чисел/дат и упаковку native wheel. Отсутствие
этой зависимости не мешает первой реализации; schema и fixtures одинаковы
при любом serializer. Неконечные числа не включаются в контракт события.

## .NET

### Прикладной API

Зависимость прикладных классов — `ILogger<T>`. Частые и повторяемые сообщения
оформлять методами с `LoggerMessageAttribute`; Serilog подключать на уровне
host/provider. Для современного .NET это основной путь оптимизации подготовки
сообщений. Он не устраняет работу Serilog sink, JSON formatter и диска.
[Source generation](https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/source-generation),
[Serilog provider](https://github.com/serilog/serilog-extensions-logging).

```csharp
using Microsoft.Extensions.Logging;

/// <summary>Технические события поиска с заранее определёнными полями.</summary>
public static partial class SearchLog
{
    /// <summary>Записывает готовый итог; длительность передаётся в миллисекундах.</summary>
    [LoggerMessage(
        EventId = 61001,
        EventName = "search.finished",
        Level = LogLevel.Information,
        Message = "Search {OperationId}: {ResultCount} nodes in {DurationMs} ms")]
    public static partial void Finished(
        ILogger logger, string operationId, int resultCount, double durationMs);
}
```

Вызывать `SearchLog.Finished(logger, operationId, resultCount, durationMs)` после
поиска. Уровень по умолчанию проверяет generated code. Если нужно вычислить
дорогую диагностическую сводку, сначала проверяется `logger.IsEnabled(...)`;
не отключать generated check через `SkipEnabledCheck` без доказанного владения
всеми вызывающими местами. Обычный структурированный `LogInformation` допустим
для редких сообщений; переписывать ради него весь существующий проект не нужно.

Полные бизнес-объекты через `{@Object}` в горячем пути не передаются. Вместо них
логируются разрешённые скалярные поля. Exception передаётся как exception в
техническом logger только на выбранной границе; история получает безопасный
error code. Ни `ToString()`, ни сериализация exception заранее не нужны.

Поля generated logging (`OperationId`, `ResultCount`, `DurationMs`) и schema
журнала (`operation_id`, `result_count`, `duration_ms`) связываются явным DTO
mapper. Текст RenderedMessage и внутренняя форма Serilog EventId не используются
как межплатформенный контракт. Нужные scope/enrichers подключаются и проверяются
в host; наличия `BeginScope` в коде недостаточно для доказательства его вывода.

### Serilog и writer

Для обычного файлового sink допустим `Serilog.Sinks.Async` с явным `bufferSize`,
`blockWhenFull=false` и мониторингом `DroppedMessagesCount`. Это очередь по
количеству объектов, а не гарантия байтового бюджета. Большие properties
ограничиваются отдельно. Не добавлять async wrapper поверх sink, который уже
имеет собственный асинхронный batching, без причины.
[Serilog Async](https://github.com/serilog/serilog-sinks-async).

`WriteTo.Async` переносит sink в worker thread, но сам по себе не объединяет
события в дисковые пакеты. Для технического файла буферизацию задавать явно:
`buffered=true`; период полного flush задавать `flushToDiskInterval`, например
одна секунда. Это диагностический профиль с допустимой потерей хвоста.
Для ActivityJournal применяется общий writer-контракт ниже.
[Serilog File](https://github.com/serilog/serilog-sinks-file#performance).

Собственный writer на .NET использует ограниченный Channel или эквивалент.
Для no-wait режима выбирать `BoundedChannelFullMode.Wait` и вызывать `TryWrite`:
при заполнении он сразу вернёт false, который увеличивает счётчик потерь.
Не использовать здесь ожидающий `WriteAsync`. Не считать успешный `TryWrite` доказательством
сохранения старого элемента при режимах автоматического DropOldest/DropWrite.
Если writer один, фиксируется single-reader; producers могут быть несколькими.
`AllowSynchronousContinuations=false` не позволяет producer выполнять работу
reader inline. Логи не оборачиваются в `Task.Run` на каждую запись.
[Channel full modes](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels#full-mode-behavior).

## Общий профиль ActivityJournal

Ниже указаны логические настройки сервиса. Namespace задаёт приложение, например
`AgentActivity` в Atlas и AgMemory. Это параметры будущего adapter, а не готовые
универсальные параметры Serilog/structlog. Менять размер через browser нельзя.

| Параметр | Значение v1 | Правило |
| --- | --- | --- |
| `MaxSizeMb` | 50 | Десятичные МБ; все segment/index/manifest/temp файлы вместе |
| `AgeRetention` | Выключено | Не удалять по возрасту |
| `RecordCountRetention` | Выключено | Нет лимита 10 000 сохранённых записей |
| `MaxEventBytes` | 8192 | Включая сериализованный envelope |
| `QueryPreviewMaxChars` | 512 | Только при разрешённом preview и отдельной проверке UTF-8/JSON бюджета |
| `QueueMaxItems` | 1024 | Ограничение очереди, а не истории на диске |
| `QueueMaxBytes` | 1 048 576 | Бюджет ограниченного сериализуемого payload; overhead runtime измеряется отдельно |
| `EnqueueTimeoutMs` | 0 | По умолчанию попытка без ожидания; при заполнении drop и счётчик |
| `BatchMaxBytes` | 65 536 | Верхняя граница пачки, событие не разрезается |
| `BatchMaxDelayMs` | 250 | С момента первого принятого события пачки; пустых пробуждений/записей нет |
| `Durability` | `durable-batch` | Полная синхронизация после пачки; публикация только подтверждённого commit |
| `ShutdownDrainTimeoutMs` | 2000 | Ограниченное ожидание завершения; не обещает выгрузить всю очередь при зависшем диске |

Настройки принадлежат сервису и в v1 читаются при старте/рестарте. Увеличение
MaxSizeMb сохраняет историю; уменьшение сначала вытесняет старые сегменты, затем
активирует новую квоту. Нулевые, отрицательные, переполняющие вычисления и
несовместимые значения возвращают configuration error, без неограниченного
fallback. MaxEventBytes должен помещаться в batch/queue; segment и служебный
резерв — в дисковый budget. Все writers общего каталога согласуют одну квоту.

QueueMaxItems/QueueMaxBytes относятся к одной очереди producer-процесса. Несколько
независимых MCP-процессов имеют суммарную память очередей пропорционально их числу;
не выдавать локальный лимит 1 МиБ за глобальный. Если нужен общий RAM budget,
он обеспечивается общим coordinator либо лимитом процессов и суммой их квот.
Дисковый MaxSizeMb при этом остаётся единым для общего журнала.

Если проекту требуется небольшой bounded wait, `EnqueueTimeoutMs` можно поднять
до 10 мс с отдельным замером event loop/request latency; для Atlas/AgMemory
v1 выбирается 0. Сроки batch/shutdown — целевые дедлайны ожидания, а не гарантия
времени системного вызова диска при неисправном накопителе.

Два лимита очереди действуют одновременно. В ней находятся уже ограниченные
immutable snapshots. Байтами считается консервативная верхняя граница
сериализованного payload с escaping; это не точный размер объектов Python/.NET
в heap. После сериализации writer проверяет реальную длину. Резерв/освобождение
бюджета выполняются атомарно и при отказе enqueue не оставляют занятый счётчик.

Шаги writer:

1. Дождаться первого элемента без polling пустой очереди.
2. Собрать пачку до byte limit либо deadline первого элемента, не продлевая
   deadline каждым новым событием. Подготовить JSON payload один раз вне
   дискового lock; служебные поля commit добавляются после назначения sequence.
3. Под единственным writer/межпроцессным lock проверить quota и конфигурацию,
   выполнить ротацию при необходимости, назначить sequence и записать пачку.
   При назначении sequence финальная длина envelope проверяется повторно.
4. Выполнить требуемую синхронизацию данных и metadata recovery protocol.
   После успешного commit обновить durable cursor и разбудить подписчиков.
5. Освободить память пачки. Медленный WebSocket не задерживает writer.

Byte limit может вызвать flush раньше 250 мс. При большой нагрузке это повышает
число sync; выбор размера и частоты проверяется на burst. В многопроцессном
режиме нужны ограниченная пачка на одного владельца lock и защита от starvation.

Последовательная запись ведётся в открытый segment; файл не открывается заново
для каждого события. Не делать `stat` всех файлов, checkpoint metadata, обход
каталога и ротацию на каждую запись. Восстановленный учёт байтов обновляется
при append и изменениях сегментов; ограниченная сверка проводится при запуске
и ротации. До увеличения файлов освобождается место с учётом служебного резерва.

## Flush, надёжность и восстановление

| Состояние | Что известно |
| --- | --- |
| Accepted | Событие принято ограниченной очередью в RAM |
| Written | Байты переданы файловому потоку/ОС; гарантии durable ещё нет |
| Persisted | Успешно завершён commit с требуемой синхронизацией и recovery metadata |
| Delivered | Конкретный подписчик применил событие; это отдельное подтверждение |

В Python для buffered file сначала вызывается `flush()`, затем `os.fsync()`.
В .NET `StreamWriter` сначала сбрасывает собственный буфер, затем для его
FileStream применяется `Flush(flushToDisk: true)`. Обычный `FlushAsync()` не
приравнивается автоматически к полной синхронизации накопителя.
[Python fsync](https://docs.python.org/3/library/os.html#os.fsync),
[FileStream.Flush](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=net-10.0).

Для create/rename/delete manifest и сегментов нужен согласованный с целевой ОС
recovery protocol, включая синхронизацию каталога там, где это требуется и
поддерживается. Один fsync файла не доказывает crash-safe переименование.
Гарантии ОС/контроллера/накопителя проверяются в пределах заявленного deployment;
слово persisted не означает защиту от любого аппаратного отказа.

Профиль `durable-batch` синхронизирует пачку до live publication. Это выбранный
профиль Atlas/AgMemory. Потеря pending RAM при crash допускается; уже
опубликованный persisted cursor не должен указывать в неподтверждённый хвост.

Более экономный профиль с полной синхронизацией раз в секунду разрешён только
как отдельная настройка и отдельный контракт. Либо публикация тоже ждёт sync
и увеличивает задержку до примерно секунды плюс I/O, либо live события отмечаются
written, отдельно передаётся durable cursor и проверяется rollback после crash.
Нельзя молча включить такой профиль и сохранить обещание persisted live до 500 мс.

При shutdown прекращается intake, закрывается очередь и выполняется drain
до timeout. Недоставленный остаток отражается в health/метриках, когда это
возможно; при внезапном crash точный размер потери может быть неизвестен.
Timeout не отменяет физически уже начатый зависший fsync и не разрешает
освободить файл под работающим writer. Dispose/stop выполняется владельцем host.

## Объём записи и нагрузка на диск

Квота хранения не ограничивает суммарные записи за сутки. При 20 событиях/с
по 1000 байт получается 1 728 000 000 байт, около 1,73 ГБ/сутки до служебных
расходов. Полезная ёмкость 50 МБ при таком постоянном потоке — не более примерно
42 минут; реальное окно меньше из-за metadata и ротации. Длительная история
получается при меньшей средней активности.

Уменьшать количество операций I/O пакетами; уменьшать байты короткими полями,
отсутствием дублей и агрегированием необязательных подробностей. Started/finished
и ошибки не сэмплируются в штатном режиме. При вынужденной потере история
отмечается неполной; очередь не сохраняет полноту ценой остановки сервиса.

В v1 нет сжатия во время ротации, повторного копирования всего журнала и
обязательного ежедневного archive. Удаляются старые закрытые сегменты. Reading
history идёт ограниченными страницами; WebSocket читает хвост по cursor, а
анимация работает из памяти. Новые записи не заставляют перечитывать все 50 МБ.

При необходимости строгого write-rate budget вводить отдельный token bucket
на bytes/sec и ограниченный burst. Превышение приводит к счётчику потерь или
отключению необязательных деталей, а не к бесконечной очереди. Такой budget
не равен MaxSizeMb и не ограничивает чужие записи приложения или фактическую
write amplification SSD. По умолчанию отдельного rate cap нет.

Ротация по размеру Loguru и `fileSizeLimitBytes`/`retainedFileCountLimit` Serilog
сами по себе не доказывают общий строгий предел всех файлов, metadata и
временных копий. Для точной квоты используется наш journal adapter; для
технических логов приложения устанавливается отдельная политика хранения.

## Трансляция событий в интерфейс

Для локальных Atlas/AgMemory v1 выбран обычный WebSocket с компактным JSON и
подтверждениями применения пакетов. Журнал и reducer используют независимый
контракт подписки, поэтому транспорт можно заменить адаптером без изменения
событий и дискового формата. SSE — предусмотренная альтернатива для других
односторонних consumers, а не второй обязательный транспорт первой поставки.

| Вариант | Свойства | Решение |
| --- | --- | --- |
| WebSocket | Двунаправленный канал, текст/бинарные данные; reconnect/replay и ограничение потока реализует приложение | Основной адаптер; ACK и фильтры передаются без дополнительных HTTP запросов |
| SSE / EventSource | Односторонний UTF-8 поток HTTP, встроенный reconnect и Last-Event-ID | Подходит для простой ленты; преимущество в скорости над WebSocket не доказано |
| Streaming fetch | HTTP response body читается порциями; можно управлять чтением и заголовками запроса | Допустим при необходимости специальных auth headers или управления чтением; парсер и reconnect свои |
| Polling / long polling | Повторные HTTP requests и явный cursor | Резерв для среды без streaming; частый polling не выбран базовым вариантом |
| WebTransport / WebSocketStream | Дополнительные возможности Streams/HTTP3 и управления потоком, другие требования к runtime/browser | Не требуются для v1; не вводить без измеренного ограничения основного транспорта |

SSE не делает запрос на каждое событие: это одно длительное HTTP-соединение.
Но на HTTP/1.x browser имеет небольшой общий лимит соединений к origin,
который затрагивает несколько вкладок; MDN указывает типичный лимит 6 для SSE.
HTTP/2 multiplexing снимает именно это ограничение, но его нельзя считать
автоматически включённым у localhost host.
[MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events).

У WebSocket небольшой framing: например, для одного неразбитого server frame
с payload 1000 байт и без extensions заголовок составляет 4 байта, без TCP/TLS
overhead. Это расчёт по формату, а не benchmark. Текстовые поля event/id/data
в SSE не дают основания считать его заведомо экономнее WebSocket.
[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455#section-5.2).

Выбор WebSocket здесь основан на управлении доставкой и использовании
одного канала, а не на утверждении о его универсальном превосходстве в latency.
Для исходной нагрузки 20 событий/с по 1000 байт полезный поток — 20 КБ/с на
подписчика, при 200 событиях/с — 200 КБ/с. Реальную долю транспорта, JSON,
диска и DOM устанавливают измерения; число сессий не равно числу подписчиков.

### Ограничение потока и пакеты

1. Один stream на страницу, общий для слоя, панели и всех агентов. Не открывать
   соединение на каждую сессию, курсор или карточку. Открытие/закрытие задаётся
   потребностью интерфейса; при отсутствии consumers поток закрывается.
2. После persisted commit отправлять доступные события пачкой без второго
   искусственного ожидания 250 мс. Верхние границы сообщения — 64 КиБ включая
   envelope и 128 событий; большую пачку/снимок делить на ограниченные части.
3. Сериализовать разрешённую проекцию один раз на группу одинаковых подписок
   и переиспользовать immutable bytes. Между разными authority/filter contexts
   данные и кеш проекции не переиспользуются без отдельной проверки ключа.
4. У subscriber ограничить сумму pending и sent-but-unacknowledged payload
   256 КиБ и 256 сообщениями. Положить пакет в socket buffer недостаточно:
   client подтверждает обработанный reducer пакет через application ACK.
5. ACK подтверждает messageId, а последний применённый cursor обновляется
   только после целостного snapshot либо применения event batch. ACK частей
   snapshot освобождает окно сообщений, но не объявляет весь snapshot применённым.
   Весь собираемый snapshot ограничен 256 КиБ; превышение отражается omitted
   counts, а не неограниченным накоплением подтверждённых частей в браузере.
   История не выдаёт транспортный приём за обработку приложением.
6. При исчерпании окна server прекращает добавлять bytes в socket и ждёт ACK,
   сохраняя только ограниченную очередь. При отсутствии прогресса 5 секунд,
   переполнении очереди или вытеснении replay-окна — закрыть подписку и выполнить
   reset/reconnect. Timeout означает политику consumer lag, не ошибку основной
   операции агента. Writer не ждёт сеть и не задерживает disk commit.
7. ACK принимается только для действительно отправленного messageId в текущей
   подписке/epoch; дубли безвредны, будущий/чужой ACK не расширяет окно. Control
   payload ограничен 1 КиБ, ошибки не пишутся в журнал рекурсивно.
8. UI применяет данные ограниченным reducer и группирует render через
   requestAnimationFrame. Анимационные кадры не порождают новые события журнала.
   Для foreground, background tabs и native WebView проверяются slow-consumer
   timeout, reconnect и отсутствие неограниченной browser queue.

Числа окна, message size и timeout — логические настройки stream adapter,
отдельные от дисковой квоты и producer queue. В v1 не включать compression,
MessagePack/Protobuf и полный повторный snapshot на каждое событие. Возвращаться
к этим оптимизациям только при измеренном выигрыше на реальном payload.

Обычный browser WebSocket сам не предоставляет входной backpressure; его
bufferedAmount описывает исходящие send bytes. Поэтому нужны application ACK
и ограниченное окно. WebSocketStream имеет другую поддержку browser engines;
WebTransport использует HTTP/3 и имеет отдельные требования secure context.
Это не автоматическое ускорение существующего Python/.NET host.
[WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API),
[WebTransport](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API).

### Перенос на SSE

Для альтернативного SSE adapter использовать те же snapshot/events/resetRequired
и bounded reducer. Last-Event-ID — транспортный resume ID, не подтверждение
успешной обработки reducer. Приложение ведёт собственный applied cursor; после
сбоя не перескакивает на более новый транспортный ID автоматически.
[HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html).

Нативный EventSource не предоставляет произвольный набор request headers;
потребность в bearer headers решается fetch-streaming либо принятой same-origin
авторизацией, без токена в URL. ID и фильтр не содержат текст запросов пользователя.
Для equivalence с WebSocket ACK/credit потребуется отдельный ограниченный HTTP
control channel; без него SLA slow-client protection нельзя считать тем же.

Отключить накопление ответа middleware/proxy, отдавать text/event-stream,
проверять heartbeat/flush и разрыв в реальной цепочке. Heartbeat идёт только
по сети, не добавляется в дисковый journal. При reset закрывать старый stream
и согласовывать новый applied cursor; auto-reconnect не превращать в retry loop.

В .NET 10 есть Results/TypedResults.ServerSentEvents с IAsyncEnumerable; для
других target framework проверяется доступный API, обновление runtime не требуется
ради самой идеи SSE. В Python streaming response должен корректно формировать
SSE framing, обрабатывать disconnect и сохранять ограниченную очередь.
[ASP.NET Core SSE](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.http.results.serversentevents?view=aspnetcore-10.0),
[FastAPI StreamingResponse](https://fastapi.tiangolo.com/advanced/custom-response/#streamingresponse).

### Как сравнивать транспорт

Перед заменой адаптера сравнить WS JSON и SSE JSON при одинаковых payload,
commit mode, batch size, auth projection и UI reducer. Проверить 1/5/10 вкладок,
HTTP/1.1 и реально согласованный HTTP/2, native WebView, burst и suspended tab.
Измерить event→reducer p50/p95/p99, CPU server/browser, RSS, bytes/sec, messages/sec,
число reconnect/reset, длительность replay и рост очередей медленного клиента.
Самостоятельно замерить render latency: она не равна network latency.

Менять основной транспорт только по измеренному ограничению или требованиям
среды. Сравнительный runtime benchmark WS/SSE этой инструкцией не выполнен;
выбор v1 — архитектурное решение по проверенным свойствам протоколов.

## Перегрузка и наблюдаемость самого writer

При full queue, disk full, denied delete, ошибке сериализации или несовместимой
конфигурации не менять результат/исключение основной операции. Не делать
неограниченный retry и не переходить автоматически на синхронную запись из
request thread. Использовать ограниченный backoff с верхней границей и health.

Потери классифицируются: full_queue, oversize, invalid_event, storage_unavailable,
shutdown. События могут потерять started или finished отдельно, поэтому state
reducer умеет unknown/interrupted и не объявляет успех без основания.
Отдельный служебный счётчик потерь не требует записи нового события в ту же
переполненную очередь. Fallback stderr ограничивается по частоте и размеру;
сырой payload/exception dump туда не передаётся.

Нужные метрики: accepted/dropped events, pending items/bytes, written bytes,
write batch count/size, full-sync count и duration, enqueue duration, writer lag,
last durable cursor, subscriber lag/resets, used/max bytes. Метрики используют
ограниченные labels reason/channel; session/operation/query не становятся labels.

Ошибки Serilog SelfLog и Python logging не направляются обратно в тот же
неисправный pipeline. В Serilog Async счётчик потерь снимается через inspector;
в Python политика full queue и её счётчик реализуются явно.

## Проверка перед внедрением

| Проверка | Что должно быть доказано |
| --- | --- |
| Диагностика выключена | Дорогие diagnostic suppliers и JSON не вычисляются; ActivityJournal продолжает работать |
| Включён/выключен весь journal | Результат, число бизнес-вызовов, порядок исключений и отмена не меняются |
| Burst и долгий медленный диск | Очередь ограничена, service latency измерена, потери видимы, нет синхронного fallback |
| Длинные Unicode и крупные properties | Ограничены payload и очередь; нет удержания ORM/request graph |
| Все типы ротации и ошибки удаления | Строгая общая quota соблюдена, нет дополнительных temp/archive вне бюджета |
| Crash после accepted/write/sync/rename | Отличаются pending и persisted; replay не обещает отсутствующую непрерывность |
| Конкурентные producers и clear | Нет перемешанных записей, дублей sequence и чужого контекста |
| Shutdown и повторный запуск | Drain bounded, recovery проверен; зависший I/O не маскируется успешным flush |
| Python/.NET fixtures | Одинаковы schema, UTC, единицы, Unicode, seq, epoch и cursor semantics |

Сравнивать один и тот же workload в режимах journal off, on без подписчика,
on с подписчиком и с искусственно медленным sink. Записывать p50/p95/p99
request/enqueue/commit latency, CPU, allocations/RSS, I/O bytes и sync/sec.
Зафиксировать ОС, runtime, версии пакетов, накопитель и размер событий. Для
Atlas/AgMemory исходная нагрузка — 8 сессий, 20 событий/с и burst 200 событий/с;
цели — p95 добавки к основной операции до 10 мс и event→UI до 500 мс на одной
машине. Для другого проекта численные цели выбираются по его нагрузке.

CPU, queueing, JSON и filesystem проверять отдельно. `LoggerMessage`, structlog
или async wrapper не считаются доказательством быстродействия всего pipeline.
Сначала устранить I/O в hot path и лишние события; serializer менять после замеров.
