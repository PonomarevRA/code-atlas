# Хранение проектов и безопасная оптимизация

Постоянные данные Atlas уже отделены от приложения и исходных репозиториев:

- macOS: `~/Library/Application Support/Code Atlas`;
- Windows: `%LOCALAPPDATA%/Code Atlas`;
- Linux: `$XDG_DATA_HOME/code-atlas` или `~/.local/share/code-atlas`.

Явный `--data-dir` / `ATLAS_DATA_DIR` сохраняет приоритет. Управляемые Git-клоны
живут в отдельном соседнем каталоге `Code Atlas-repositories`. Исходные
репозитории, выбранные пользователем, не копируются и не перемещаются.

Новые сборки используют `maps/projects/<projectId>/<snapshotId>/`. Старые абсолютные
пути из `projects.json` продолжают читаться: существующие снимки и внешние
Graphify MCP-конфигурации не переносятся и не переписываются. Внутри снимка:

| Данные | Назначение и срок хранения |
| --- | --- |
| `atlas-graph.json` | Канонические факты, неизменяемая история; автоматически не удаляется. |
| `graphify-out/graph.json` | Оригинальный результат провайдера; сохраняется без изменения байтов. |
| `mcp-graph.json` | Более крупная совместимая проекция Graphify. В новых ревизиях создаётся только при Graphify describe/query/export, а не для обычного agent MCP. |
| `graphify-out/cache/` | Кеш конкретного extraction worker. Следующий build получает другой snapshot ID и его не использует; после завершения worker кеш удаляется. |
| `atlas-grouped-*.json` | Восстанавливаемая группировка. Офлайн-очистка убирает известные варианты из прошлых снимков; у текущего сохраняет их для быстрого открытия. |

Проекция Graphify строится из того же канонического снимка под блокировкой,
без потери атрибутов, полей и параллельных отношений. Ошибка создания проекции
даёт 503 и допускает повтор запроса, сохраняя доступную карту. У старых ревизий
без признака lazy missing-файл остаётся ошибкой: тихого отката к raw нет.
Существующие экспортированные проекции не очищаются — их пути могли сохраниться
во внешних клиентах. Обычный agent MCP читает каноническую карту напрямую.

## Отчёт и очистка

В установленной сборке, содержащей эти изменения, команды доступны у `CodeAtlas`.
Из рабочей копии:

```sh
.venv/bin/python -m atlas.cli --storage-report
.venv/bin/python -m atlas.cli --optimize-storage
```

Для другого каталога добавьте `--data-dir <путь>`. Отчёт ничего не удаляет.
Оптимизация требует остановить Atlas и захватывает ту же межпроцессную блокировку,
что сервер; при работающем приложении операция отклоняется до удаления файлов.
Она удаляет только два перечисленных вида кешей в зарегистрированных проектах.
Ссылки и junction не обходятся; неизвестные проекты/файлы не трогаются.

История снимков, исходники, raw-графы, MCP-проекции, сохранённые виды, health records,
исследования, справочники и модели не удаляются. Операция повторяема: второй запуск
без новых кешей освобождает ноль байт. При частичной ошибке JSON-отчёт содержит
`status: partial` и пути ошибок. Счётчик `removedBytes` — логический размер;
фактически освобождённые блоки могут отличаться на APFS/сжатых файловых системах.

Автоматического удаления старых снимков нет. Для архивации истории нужен
отдельный контракт с проверкой сохранённых видов, записей здоровья, исследований
и внешних MCP-ссылок; число последних снимков само по себе не доказывает, что
остальные больше никому не нужны.

Для явного удаления выбранных карт через интерфейс доступна отдельная
[очистка снимков](map-cleanup.md). Она требует просмотра последствий и
подтверждения; ограничения команды оптимизации кешей не являются запретом
на эту отдельно выбранную операцию. Исходники и записи для пересборки сохраняются.

Результат применения 18 октября: `outputs/project-storage-20261018/validation.md`.
Отдельный список резервных ZIP для выбранного пользователем срока хранения:
`outputs/project-storage-20261018/backup-retention-plan.md`. Очистка кешей эти
архивы не затрагивает.

## Резервные копии: три последних автоматических ZIP

Команда `--backup-data`, используемая установщиком перед обновлением, сохраняет
данные в соседнем каталоге `Code Atlas-backups`. После успешного завершения нового
ZIP автоматически остаются три последние копии. При ошибке записи предыдущие
копии не удаляются. Правило работает в сборках с модулем `atlas/backup_retention.py`.

Автоматическими считаются только обычные файлы с именем
`YYYYMMDDTHHMMSSZ-xxxxxxxx.zip` и корректной датой. Ручные именные архивы,
каталоги резервных копий, незавершённые файлы и ссылки сохраняются. Порядок задаётся
датой в имени; для одной секунды — временем завершения записи и затем именем.
Перед удалением проверяется читаемость центрального каталога трёх сохраняемых ZIP.
Это не полная проверка CRC или пробное восстановление. Ошибка проверки оставляет
старые копии; ошибка удаления может оставить лишние архивы и требует повторения.

Очистка синхронизируется файлом `.retention.lock` в каталоге копий. Само создание
backup по-прежнему требует остановленного сервера и блокировки `server.lock`.
История снимков внутри рабочего каталога данных этим правилом не ограничивается.

## Единая папка карт

Новые карты живут в `maps/` внутри выбранного каталога данных Atlas:

- `maps/projects/<projectId>/<snapshotId>/` — снимки кода;
- `maps/data-maps/catalog.json` — каталог карт данных;
- `maps/data-maps/<mapId>/<snapshotId>/` — захваченные источники, метаданные и SQLite;
- `maps/data-maps/<mapId>/views/` — сохранённые виды данных;
- `maps/views/` — сохранённые виды графа кода.

Запуск и GET ничего не переносят, не копируют и не перестраивают. Если нового
каталога карт данных ещё нет, читается `data-maps/catalog.json`. Первое явное
изменение атомарно публикует весь загруженный каталог в `maps/data-maps/` с теми
же ID и записями. После этого новый каталог является единственным источником:
старые записи не подмешиваются обратно после перезапуска.

Для выбранного mapId/snapshotId чтение сначала проверяет новый каталог снимка,
затем старый `data-maps/<mapId>/<snapshotId>/`, если нового нет. Если новый снимок
существует, но повреждён, отката к старой копии нет. Виды читаются аналогично;
список кодовых видов объединяет старую и новую папки по UUID с приоритетом новой.
Старые абсолютные пути к графам, экспортам и внешним MCP остаются действующими.
Отчёт и очистка учитывают три расположения кодовых снимков: `<projectId>/`,
`projects/<projectId>/` и `maps/projects/<projectId>/`.

Потеря снимка, metadata.json или records.sqlite возвращает `SNAPSHOT_MISSING`,
неверные обязательные метаданные или схема SQLite — `SNAPSHOT_CORRUPT`, опасный
путь/ссылка/конфликт файла и папки — `INVALID_STORAGE` (HTTP 409). Обзор, список и
техническая страница продолжают работать и показывают `freshness.status=unavailable`
с причиной, сохраняя ID снимка. Эти чтения не меняют сохранённый статус и не
подставляют нулевые показатели вместо недоступных. Прямые запросы и экспорт
возвращают структурированную ошибку. Явное «Обновить» создаёт новое задание и
публикует отдельный исправленный снимок; повреждённая история не удаляется.

## Компактные снимки кода: manifest и общие объекты

Новые сборки записывают `atlas-graph.json` как manifest версии
`atlas-snapshot-objects-v1`. Читатель `ProjectStore` распознаёт прежний полный JSON
и новый manifest; существующие снимки не мигрируются при запуске или чтении.

Объекты находятся в `maps/projects/<projectId>/_objects/<prefix>/<sha256>.json.gz`.
Один объект содержит ограниченную группу узлов одного исходного файла либо
группу его исходящих связей. Объекты ограничены 256 записями и целевым объёмом
1 МиБ; отдельная большая запись допустима до жёсткого предела 16 МиБ объекта.
Объектный JSON кодируется детерминированно и сжимается независимо. Manifest
сохраняет первоначальный порядок узлов и связей, включая параллельные рёбра.

Идентификаторы Graphify и отображаемые названия остаются прежними. Только внутри
чанка связей повторяющиеся endpoints заменяются индексами локальной таблицы.
Повторяющийся `codeProjectFacts` хранится в общей таблице по хэшу содержания;
добавление нового значения не меняет ссылки уже существующих узлов. Неизменённые
объекты следующего снимка переиспользуются без перезаписи. Метаданные и результаты
обогащения сохраняются полностью, включая действующий health codec.

Значения `node.health.measuredAt` вынесены в отдельную таблицу снимка. В исходном
DTO восстанавливается точное значение каждого узла, включая отсутствие поля,
`null` и отличающиеся значения. Обновление времени повторной оценки не переписывает
стабильные node objects. Проверка реального `ProjectStore` с обычным enrichment
подтверждает переиспользование узлов при неизменённых исходниках.

Публикация сначала завершает immutable objects и только затем атомарно заменяет
manifest. Конкурирующие writers создают один объект без замены существующего
содержимого. Чтение проверяет SHA-256, точную длину распаковки, окончание gzip,
схему и координаты записей. Неизвестная версия, потерянный объект, повреждение
или перенаправление через symlink дают ошибку карты; тихого возврата частичного
графа нет. Ограничены размер manifest, отдельного объекта, число записей и общая
распаковка. Зависимые кэши включают идентичность manifest и stat-ревизии всех
объектов; LRU учитывает логический объём графа, а не маленький размер manifest.

Raw-результат Graphify и уже выданные файлы MCP остаются обычными совместимыми
JSON. MCP-проекция нового снимка по-прежнему материализуется лениво. Старые
объекты автоматически не удаляются: будущий сборщик должен учитывать ссылки
всех сохранённых manifest, видов, исследований и экспортов. Срок idle-кэша
рабочей задачи не является сроком жизни постоянных объектов снимка.

Этот формат уменьшает диск и повторное хранение истории. Текущий общий читатель
восстанавливает полный граф для существующих потребителей; размер сжатого объекта
не является оценкой RSS или обещанием адресного чтения без распаковки всего графа.
Прочитанные чанки освобождаются после последнего нужного элемента; точная проверка
логического JSON-размера выполняется по отдельным записям без второй полной строки
графа. Ограничения фонового health-пересчёта и semantic retention используют
логический размер снимка, поэтому маленький manifest не обходит прежние квоты.
