# Необязательные локальные движки

Atlas открывает базовую карту сразу. При работе с картой приложение само проверяет
доступные движки, сохраняя положительный или отрицательный результат примерно на
24 часа. Агент не нужен. В разделе «Моды и движок» у каждого семантического мода
есть автоматический поиск, явные пути, возврат к автоматическому выбору и проверка
совместимости с выбранной опубликованной картой. Явный неверный путь не заменяется
другим исполняемым файлом.

Рядом с каждым путём кнопка «Автоматически» убирает только его сохранённое
значение. Общая кнопка «Автоматический выбор» сбрасывает все пути этого мода.
«Найти установленные пути» выполняет ограниченный поиск существующих файлов;
«Подставить» меняет черновик, а запись выполняется кнопкой «Сохранить пути».
Наличие файла не подтверждает совместимость движка.

Для агентов доступны `inspect_semantic_engine_settings` и
`set_semantic_engine_paths`, а также одинаковый HTTP-контракт:
`GET /api/semantic-engines/settings`,
`GET /api/mods/{modId}/semantic-engine-diagnostics?projectId=ID` и
`POST /api/mods/{modId}/semantic-engine-settings`.
Тело `{"mode":"patch","paths":{"pythonPath":""}}` возвращает одно поле
к автопоиску, сохраняя остальные; `{"mode":"replace","paths":{}}` сбрасывает
весь мод. Пути общие для мода на компьютере и влияют на все карты.
Браузерный агент может пользоваться самой страницей и same-origin API без MCP.
`/engine-setup.html`, `/api/agent-setup` и `/agent-setup.md` описывают возможности и порядок действий;
изменение настроек выполняется в рамках поручения пользователя.

Описание выбранного метода ставит ограниченное уточнение в фон. Наличие runtime,
наличие анализатора, подходящий контекст проекта и применённые факты — разные
состояния. Приложение ничего не устанавливает, не выполняет сборку/restore
анализируемого проекта и не запускает его модули. Установленные движки являются
доверенным локальным кодом; ограничения процессов не заменяют песочницу ОС.

| Мод | Доступные уточнения | Граница текущей реализации |
| --- | --- | --- |
| C# | Roslyn: тип получателя, перегрузки, extension methods, assembly origin | Подтверждение требует полного ограниченного простого проекта и references; фрагменты, неучтённый MSBuild/генерация и ошибки компиляции оставляют кандидатов. `nameof` не попадает в новые факты вызовов. |
| TypeScript | Существующий Compiler API TS5: определения и цели-кандидаты | Ambient types, стандартная библиотека и полный project/reference context не доказаны; подтверждённые вызовы не добавляются. |
| JavaScript | Тот же установленный TS5 для JS/JSX, ESM/CommonJS и JSDoc | Отдельный мод и языковой scope; определения остаются кандидатами. |
| Python | Jedi 0.19/0.20 и Parso в существующем Python/venv | Только ссылки на исходные определения; динамические вызовы, внешнее окружение и stubs не квалифицированы. |
| C++ | clangd 14–23 и существующий compilation database | Подтверждение требует доказанного замыкания захваченных include; пропущенные заголовки/макросы/контекст оставляют кандидатов. Стандартные заголовки не догружаются. |
| Java | JDT LS, существующий JDK21+ и статический `.classpath` | Изолированный source-only Eclipse context; без Maven/Gradle/builders/annotation processing. Кандидаты. |
| Go | gopls v0 и существующий Go, ограниченный `go.mod` | Offline, без cgo/package-driver/toolchain downloads; кандидаты. |
| Rust | rust-analyzer и существующий `rust-project.json` | Без Cargo, build scripts, proc macros и внешнего sysroot; кандидаты. |
| Swift | SourceKit-LSP семейства Swift6, compilation database и SDK | Без SwiftPM/BSP/background indexing/builds; кандидаты. |
| PHP | Phpactor семейства 2026, PHP8.2+ и необходимые расширения | Private source context, без Composer bootstrap/проектных конфигураций; кандидаты. |
| Kotlin | Обнаружение установленного движка | Семантический worker отложен: безопасный статический importer не квалифицирован. Сохраняется базовый анализ. |

Локально на macOS проверены реальные SDK8.0.403/10.0.102, TypeScript5.9.2
с Node24.5.0 и clangd19.1.7. Машина ARM64, но процесс Python и проверенный
clangd работают как x86_64; это не подтверждение нативной ARM64-поставки.
Для остальных движков проверены контракты,
отсутствие/неподходящий контекст и fallback, а не нативная семантика.
Другие ОС и архитектуры нативно не квалифицированы.

## Связь с Graphify и метриками

Graphify остаётся базовым механизмом. Исходные файлы графа и raw ID не переписываются.
Отдельный source-bound overlay хранит ограниченную область уточнения и объединяется
для карты, описаний, соседей, входных данных health и MCP. Новый запрос заменяет
предыдущую ограниченную область; полного накопительного индекса пока нет.

Кандидат не становится подтверждённым ребром. Неоднозначный символ и недостающая
зависимость остаются неизвестными. Статическая связь не доказывает runtime dispatch.
Сохранённые оценки H/O автоматически не пересчитываются: этот слой не устраняет
все причины UNKNOWN и не объявляет отсутствующие рекомендации успешными.
При выключении мода или несовпадении снимка его overlay не применяется.

Публикация повторно проверяет исходные байты, конфигурацию, выбранные моды,
актуальность результата/движка и уникальную эпоху состояния. Проверки исходников
выполняются в фоне перед публикацией, не на каждом тёплом чтении карты.

## Как отличать готовность движка от применения

`availability` описывает обнаружение движка, а `enrichment` — работу с выбранной
областью. `applied` появляется только после успешной записи overlay, содержащего
хотя бы один факт с проверенной привязкой к исходному узлу. Принятый кандидат или
неизвестный результат тоже является фактом; отсутствие подтверждённых рёбер не
превращает его в ошибку движка и не подтверждает runtime dispatch.

Каждая пара provider/target содержит ограниченный `outcome`: `rawFacts`,
`projectedFacts`, `rejectedFacts`, `confirmedEdges`, `queryCount` и `reasons`.
Счётчики проекции относятся к опубликованной области; при ошибке записи они
остаются нулевыми. `resultStatus` сохраняет статус callback, когда он состоялся.
Причины различают `analysis-unsupported`, `no-queries`, `no-source-bindings`,
отброшенные привязки и ошибку движка. Произвольный текст диагностики и локальные
пути не копируются в новые причины; сохраняется до восьми кодов по96символов.

Обязательные `rust-project.json` и `.classpath`, как другие известные файлы
контекста, участвуют в идентичности конфигурации: их создание, изменение или
удаление пересматривает состояние при обычном использовании. Изменение известной
среды поиска также меняет только закрытый хэш, без выдачи значений переменных.
Новый executable при неизменной среде всё ещё может потребовать явной повторной
проверки до истечения обычного discovery TTL.

## Догрузка AST

В описании метода раздел «Структура AST · есть ли глубже» открывает прямых потомков,
родителя и следующую страницу. HTTP и дополнительный MCP-инструмент используют
одинаковые ссылки, закреплённые за узлом, снимком и хешами исходника.
Это синтаксический обзор; порядок исполнения и цели вызовов здесь не вычисляются.

Лимиты method-flow 20 000 узлов тела / 180 шагов / глубина24 сохранены.
На запрос AST возвращается до64 детей и64КБ. Сохраняемого дерева чанков пока нет:
каждый запрос разбирает целиком исходный файл в пределах существующего лимита1МБ.

## Поставка

В приложение входят адаптеры Atlas и физические worker-файлы. В текущем наборе данных упаковки
их данные занимают41 317байт: TS worker10 201, Python worker4357,
C# bridge26 624 и runtimeconfig135. Это не размер всего приложения и не бюджет RSS.
Ещё74 606байт составляют восемь физических файлов кода Atlas для проверки
идентичности LSP/PHP-профилей вне PYZ; всего этих ресурсов115 923байта.
Node, .NET, Roslyn, JDT, SDK и другие движки в комплект не копируются.

`packaging/build.py` собирает только маленький bridge офлайн, если на машине сборки
уже есть SDK8. Можно указать `--roslyn-worker-root` с готовыми двумя файлами.
Без такого входа C# остаётся необязательным профилем с явным `workerPath`.
Во время работы с картой компиляция bridge не запускается.

См. [контракты модов](analysis-mods.md) и [настройку LSP](semantic-engines-lsp.md).
