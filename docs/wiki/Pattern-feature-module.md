# Модуль как класс или папка

Выделите одну ответственность и небольшой публичный контракт; класс и связная папка — допустимые границы.

## Задача

Потребители обращаются к деталям разных частей кода, поэтому локальное изменение требует синхронной правки всего приложения.

## Когда применять

- Изменения одной функции разбросаны между несвязанными файлами.
- Несколько функций разделяют один источник состояния и понятный жизненный цикл.

## Когда не применять

- Одна чистая функция решает задачу без собственной структуры.
- Папка названа общим словом helpers и объединяет случайные обязанности.

## Граница класса или папки

Класс с состоянием либо папка с публичной точкой входа; отдельный файл сам по себе не доказывает модульность.

## Ответственность

- Определить продуктовую ответственность.
- Скрыть детали хранения и вспомогательные операции от потребителей.

## Публичный контракт

Публичный calculate(items) возвращает результат; внутреннее представление не раскрывается.

## Зависимости

- Потребитель импортирует публичный интерфейс.
- Нет обратного импорта потребителя из модуля.

## Состояние и время жизни

Состояние принадлежит экземпляру или явно переданному контексту, а не глобальной переменной.

## Ошибки

- Некорректный вход отклоняется до изменения состояния.

## Пример

```python
class InvoiceTotals:
    """Считает сумму переданных целочисленных сумм в копейках."""
    def calculate(self, amounts):
        return sum(amounts)
```

Вычисление имеет один вход и результат; тот же контракт может быть функцией внутри папки invoices.

## Контрпример

```python
class Everything:
    def calculate_and_render(self, db, amounts, screen):
        db.save(amounts)
        screen.show(sum(amounts))
```

Сохранение, вычисление и UI связаны одной операцией без самостоятельных контрактов.

## Как внедрять

- Найдите потребителей и общий жизненный цикл.
- Выделите публичный вход и перенесите детали за него.

## Ограничения

- Большой файл — сигнал для анализа, а не доказательство плохой границы.
- Папочная структура не является безусловным эталоном архитектуры.

## Что проверять

- Проверить модуль без UI и базы.
- Изменить внутреннюю реализацию без изменения потребителя.

## Альтернативы

- Оставить простую функцию, если отдельный модуль не даёт пользы.

## Как писать код

- Описание метода объясняет вход, результат и существенные ошибки; комментарий ветви объясняет причину.
- Используйте ясные локальные этапы и ранние выходы; новый класс или интерфейс нужен только для самостоятельной ответственности.
