# Контрактная проверка и квалификация применения

Проверяйте реальный адаптер и тестовый двойник по одному контракту; статус карточки не доказывает успешное применение.

ID: `contract-qualification` · версия: `1.0.0` · статус карточки: **draft**.

Content hash: `d1e24a0edb00daf5f84f65c1661fbee5c9f4bbd3737c023b72aa2a7004ec51c8`.

Catalog version: `3b1765c0fa5449368237cddb8631362e34807809260037307e3e8e95780f3fa5`.

Квалификация применения в проекте: **not-assessed**. Чтение карточки не подтверждает внедрение.

## Задача

Fixture тесты проходят, хотя реальный transport, backend или caller ведут себя иначе.

## Когда применять

- Нужна замена адаптера или обновление его реализации.
- Проверки должны различать source, integration и installed runtime.

## Когда не применять

- Ожидаемое поведение выводится только из случайного результата реализации.

## Граница класса или папки

Папка contract fixtures и test adapter отделена от production use case.

## Ответственность

- Проверить нормальный/ошибочный результат.
- Сохранить identity версии проверенного потребителя и evidence.

## Публичный контракт

Одинаковый acceptance contract применяется к test adapter и реальному пути; missing evidence остаётся unknown.

## Зависимости

- Production код не импортирует test harness.

## Состояние и время жизни

Фикстура изолирована; проверки не изменяют пользовательские данные.

## Ошибки

- Недоступный runtime означает not-assessed, а не PASS.

## Пример

```python
def assert_result_contract(result):
    """Проверяет минимальную форму результата, не его истинность."""
    assert result["status"] in {"known", "unknown"}
    if result["status"] == "unknown":
        assert result["value"] is None
```

Проверка формы явно ограничена и должна дополняться смысловыми и integration cases.

## Контрпример

```python
def assert_result_contract(result):
    assert result
```

Непустой dict не доказывает согласованный контракт.

## Как внедрять

- Зафиксируйте acceptance до изменения реализации.
- Запустите один контракт для реального и тестового адаптеров.

## Ограничения

- Unit PASS не доказывает installation, accessibility или live compatibility.

## Что проверять

- Проверить отрицательный результат и degraded dependency.
- Связать отчёт с точной revision/consumer identity.

## Альтернативы

- Оставить not-assessed до появления нужного evidence.

## Как писать код

- Описание метода объясняет вход, результат и существенные ошибки; комментарий ветви объясняет причину.
- Используйте ясные локальные этапы и ранние выходы; новый класс или интерфейс нужен только для самостоятельной ответственности.

## Применимость и версии

- python
- Примеры: синтаксис Python 3.12/3.13; типизированные интерфейсы не заменяют runtime-проверки.

Инженерная рекомендация для проверки на конкретном проекте; не автоматическое правило рефакторинга.

Примеры проверяются синтаксически при сборке каталога. Они не исполняются и не доказывают поведение реального backend или MCP-клиента.
