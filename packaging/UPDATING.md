# Обновление локальной установки

Постоянные точки входа — `packaging/update-local.sh` для macOS/Linux и
`packaging/update-local.ps1` для Windows. Команды можно запускать из любой папки,
указав путь к скрипту. Ни даты, ни имя пользователя, ни PID менять не нужно.
Перед обновлением закройте окно Atlas и остановите сервер с тем же каталогом
данных. Скрипты намеренно не завершают процессы: среди них могут быть MCP,
индексация и отдельные предпросмотры. Проверка блокировки отменит обновление,
если сервер ещё работает.

## Повседневные команды

Из корня репозитория, собрать текущий код, проверить и установить:

```sh
sh packaging/update-local.sh --build
```

На Apple Silicon, включая M4 Pro, выбирается **ARM64**, даже если терминал
работает через Rosetta. Сначала ищется подготовленное окружение
`build/arm64-runtime/.venv-arm64/bin/python`, затем `.venv/bin/python` и Python
из PATH. Подходит только интерпретатор с целевой ABI; x64 не подставляется вместо
ARM64. Для другой подготовленной среды:

```sh
sh packaging/update-local.sh --build --python /path/to/native-venv/bin/python
```

Установить **уже собранную** версию из `dist`, не пересобирая:

```sh
sh packaging/update-local.sh
# Только показать выбранные пути и архитектуру, ничего не меняя:
sh packaging/update-local.sh --build --dry-run
# Установить без последующего открытия окна:
sh packaging/update-local.sh --no-start
```

Windows PowerShell:

```powershell
.\packaging\update-local.ps1 -Build
.\packaging\update-local.ps1 -Build -Python C:\native-venv\Scripts\python.exe
.\packaging\update-local.ps1 -DryRun
```

На Windows автоопределение проверяет `.venv\Scripts\python.exe`, затем `python`.
Для экспериментальной Windows ARM64 необходим ARM64 Python и совместимые
зависимости. Готовая сборка устанавливается без параметра `-Build`.

## Что выполняет скрипт

1. Определяет ОС, архитектуру и пути. Явный `--target macos-x64` / `-Target windows-x64`
   позволяет выбрать x64; сборка требует соответствующего Python. Кросс-компиляции нет.
2. С `--build` проверяет зависимости через `pip check` и вызывает существующий
   `build.py`. Он заранее проверяет закреплённую SQL-грамматику `tree-sitter-sql==0.3.11`
   импортом и пробным разбором, компилирует документные модули, очищает кеш PyInstaller,
   восстанавливает сертифицированные ресурсы lnav и подписывает macOS bundle.
3. Проверяет архитектуру настоящего executable; на macOS — также подпись.
4. Проверяет совместимость схемы данных и отсутствие активного server lock.
5. Выполняет `--native-document-check` у готового executable с пустым PATH и без
   PYTHONHOME/PYTHONPATH. Ошибка останавливает установку до замены приложения.
6. Вызывает `install-macos.sh`, `install-linux.sh` или `install-windows.ps1`:
   staged-проверка, сохранение предыдущего приложения, замена. При ошибке
   последнего переименования установщик возвращает предыдущую версию.
7. Открывает установленное приложение, если не задан `--no-start` / `-NoStart`.
   Это запрос на запуск, а не проверка готовности GUI/API или автоматический откат
   при ошибке запуска. После запуска проверьте карту и `http://127.0.0.1:8765/api/health`.

Данные **не копируются, не архивируются и не мигрируют** при совместимом обновлении.
Каталог проектов, снимки документов, заметки и настройки остаются на месте.
Неизвестная схема требует отдельного согласованного переноса. Предыдущая версия
используется для отката неудавшейся замены; после успешной проверки установщик может
удалить свою неактивную промежуточную копию. Постоянное хранение старого приложения
не гарантируется; пользовательские каталоги данных и резервные копии не удаляются.
Политика трёх автоматических копий данных действует независимо от версий приложения.

## Свои пути и отдельный профиль

```sh
sh packaging/update-local.sh \
  --source "/path/to/release/Code Atlas.app" \
  --destination "$HOME/Applications/Code Atlas.app" \
  --data-dir "$HOME/Library/Application Support/Code Atlas" --no-start
```

На Linux `--source` указывает на onedir-каталог с `CodeAtlas`, не на отдельный файл.
В PowerShell используются `-Source`, `-Destination`, `-DataDirectory`, `-NoStart`.
`--source` нельзя сочетать с `--build`: сборка всегда публикуется в `dist`.
Переменные `ATLAS_BUILD_PYTHON`, `ATLAS_BUILD_TARGET`, `ATLAS_DATA_DIR` поддерживаются;
аргументы командной строки имеют приоритет. Данные должны находиться вне приложения.

Скрипты не обновляют отдельный source-предпросмотр на порту 8893 и не перезаписывают
MCP-конфигурацию клиентов. При сохранённом пути приложения MCP использует новый
executable при следующем запуске; для новых инструментов может потребоваться
переподключение клиента.

## Подготовка машины для сборки

В уже подготовленном окружении ничего устанавливать повторно не требуется.
На новой машине создайте venv **нативным Python**, установите toolchain для C/C++
и зависимости (сеть нужна только на этапе подготовки):

```sh
/path/to/native/python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock -r packaging/requirements-build.txt
```

Windows: `C:\path\to\native\python.exe -m venv .venv`, затем
`.venv\Scripts\python.exe -m pip install -r requirements.lock -r packaging/requirements-build.txt`.
На macOS нужны Command Line Tools, на Linux — системные dev-библиотеки, на Windows
— совместимый MSVC. Зависимости не скачиваются самим скриптом обновления.
Если отдельные Command Line Tools уже установлены, macOS-скрипт использует их
через локальный `DEVELOPER_DIR`, когда переменная не задана. Глобальный выбор
Xcode и его лицензионные настройки не меняются.

Python и компилятор нужны **сборщику**, а не пользователю готового Atlas.
Установка из готового `dist` использует только системный shell и встроенный runtime.
Сертифицированный ARM64 lnav собирается отдельно при изменении vendor pack:
`python packaging/build_lnav_arm64.py`; повторять это при каждом обновлении Atlas
не нужно. Подробности — [README](README.md) и [матрица архитектур](BUILD-TARGETS.md).

## Границы проверки

Сценарий macOS проверяется локально тестами в изолированном временном каталоге.
Linux и PowerShell требуют своих нативных прогонов; наличие скрипта не означает,
что выпуск для этих ОС уже проверен. Для полного frozen gate console + app:
`python packaging/check_native.py`; для проверки WebView: `python scripts/smoke_desktop.py`.

21 октября 2026 на M4 Pro прошли 25 тестов оркестрации/установщиков/preflight,
`sh -n` и реальное обновление из ARM64 `dist` в отдельный временный каталог
с `--no-start`. Нативный document-check прошёл; контрольный документ сохранил
SHA256, inode и mtime, ZIP не создавался. Рабочая пользовательская установка
не менялась. В тестах Linux используются заглушки определения ОС/ABI; это
проверка shell-логики и staged-копирования, а не нативного Linux runtime.
Shell/PowerShell health-adapter Atlas пока недоступен: его результат `REVIEW/partial`
не заменяет самопроверку кода и выполненные проверки.
